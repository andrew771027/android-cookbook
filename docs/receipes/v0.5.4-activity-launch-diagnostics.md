# Diagnose Activity launches (v0.5.4)

Use process PID, Activity instance UUID, and lifecycle callbacks to check cold, warm,
and hot launches. Collect `am start -W` timing output alongside those observations.
The helpers live in `src/android_cookbook/activity_launch_diagnostics.py`; they provide
Python functions, with no command-line entry point or JSON report.

These are controlled diagnostic scenarios. The tests do not run repeated measurements,
compare timing thresholds, or detect performance regressions.

## Before you begin

Install the [project dependencies](../environment.md) and
[build the test APK](v0.4.2-test-apk-fixture.md#build-the-test-apk). Use an unlocked,
dedicated emulator running API 31 or later. Run from the repository root:

```bash
./scripts/build-test-apk.sh
export ANDROID_SERIAL=emulator-5554
adb devices -l
adb -s "$ANDROID_SERIAL" get-state
```

The fixture APK version is `0.5.4` (`versionCode=6`). Lifecycle logs retain marker
`android-cookbook-v0.5.1`; state logs retain `android-cookbook-v0.5.2` and include PID.
The tests reuse the existing `cookbook_finish` extra and `cookbook_action=report` hook.
See [fixture requirements](../../tests/fixtures/test-app/README.md).

Before pytest setup, the fixture package must be absent. Check for a leftover installation
and uninstall it if present:

```bash
adb -s "$ANDROID_SERIAL" shell pm list packages com.example.androidcookbook.fixture
# Run only if the package is listed:
adb -s "$ANDROID_SERIAL" uninstall com.example.androidcookbook.fixture
```

Tests install the APK with `-t`, then attempt force-stop and uninstall during teardown.
They clear the shared Logcat buffer and change the foreground Activity. Run sequentially,
without other automation using the emulator. The manual examples below assume the fixture
is already installed; remove that installation before running pytest.

## Compare the scenarios

| Scenario | Setup | PID after launch | Activity identity and callbacks |
| --- | --- | --- | --- |
| Cold | Force-stop; confirm no process | Present | New instance; `onCreate`, `onStart`, `onResume` |
| Warm | Launch, gracefully finish, wait for `onDestroy`; confirm process survived | Same PID | Different instance; `onCreate`, `onStart`, `onResume` |
| Hot | Launch, press Home, wait for `onPause`, `onStop`; confirm process survived | Same PID | Same instance; `onRestart`, `onStart`, `onResume`; no new `onCreate` |

`LaunchObservation` stores the expected type, before/after PID and UUID, a Boolean
`created_after_launch`, and the `LaunchResult`. `assert_launch_type()` checks these
observations. It does not infer the type from timing or the platform's `LaunchState`
string, and callers must collect the lifecycle evidence themselves.

`wait_until()` calls the predicate immediately, then retries every 0.2 seconds by
default for up to 10 seconds. It returns `True` on success and `False` on timeout.
A zero timeout still evaluates once; negative timeouts and nonpositive intervals raise
`ValueError`. Predicate exceptions propagate. An individual predicate call can exceed
the deadline. Unit tests use a simulated clock to verify retries without real sleeps.

### Cold launch

```bash
adb -s "$ANDROID_SERIAL" shell am force-stop com.example.androidcookbook.fixture
adb -s "$ANDROID_SERIAL" shell pidof com.example.androidcookbook.fixture
# Continue when pidof produces no PID.
adb -s "$ANDROID_SERIAL" logcat -c
adb -s "$ANDROID_SERIAL" shell am start -W \
  -n com.example.androidcookbook.fixture/.MainActivity
```

The integration test waits for a `created` state event and the new instance's
`onCreate`, `onStart`, `onResume` sequence. It checks that the process exists, the counter
is zero, and `restored` is false. `wait_until()` polls for process absence before launch.

### Warm launch

Launch once, then send the graceful finish extra to the foreground Activity:

```bash
adb -s "$ANDROID_SERIAL" shell am start -W \
  -n com.example.androidcookbook.fixture/.MainActivity
adb -s "$ANDROID_SERIAL" shell pidof com.example.androidcookbook.fixture
adb -s "$ANDROID_SERIAL" shell am start -W --activity-single-top \
  -n com.example.androidcookbook.fixture/.MainActivity --ez cookbook_finish true
```

Wait for `onDestroy` for the original UUID and check that its PID still exists. Clear
Logcat to isolate the next launch, then launch again without the finish extra:

```bash
adb -s "$ANDROID_SERIAL" shell pidof com.example.androidcookbook.fixture
adb -s "$ANDROID_SERIAL" logcat -c
adb -s "$ANDROID_SERIAL" shell am start -W \
  -n com.example.androidcookbook.fixture/.MainActivity
```

The test requires a different UUID in the same process and a new creation sequence.
It skips if the process did not survive Activity finish. Force-stopping here would remove
the existing-process precondition. `launch_activity()` uses neither `-S` nor `-R`.

### Hot launch

Launch once, record PID and UUID, and press Home:

```bash
adb -s "$ANDROID_SERIAL" shell am start -W \
  -n com.example.androidcookbook.fixture/.MainActivity
adb -s "$ANDROID_SERIAL" shell input keyevent KEYCODE_HOME
```

Wait for `onPause`, `onStop`, and confirm the original PID survived. Clear Logcat and
bring the Activity back:

```bash
adb -s "$ANDROID_SERIAL" logcat -c
adb -s "$ANDROID_SERIAL" shell am start -W \
  -n com.example.androidcookbook.fixture/.MainActivity
```

The test requires the same PID, `onRestart`, `onStart`, `onResume` for the original UUID,
and no `onCreate` in the new observation window. It then sends `cookbook_action=report`
and checks the reported UUID matches. It skips if the process disappeared during setup.

To inspect fixture logs manually:

```bash
adb -s "$ANDROID_SERIAL" logcat -d -v brief \
  'CookbookLifecycle:I' 'CookbookState:I' '*:S'
```

## Read timing output

This synthetic output is the unit-test sample, not a measured performance result:

```text
Status: ok
LaunchState: COLD
Activity: com.example.androidcookbook.fixture/.MainActivity
ThisTime: 320
TotalTime: 410
WaitTime: 435
Complete
```

| `LaunchResult` field | Source and handling |
| --- | --- |
| `status`, `launch_state`, `activity` | `Status`, `LaunchState`, `Activity` strings, or `None` if absent |
| `this_time_ms`, `total_time_ms`, `wait_time_ms` | Corresponding integer timing fields, or `None` if absent |
| `host_elapsed_ms` | Host monotonic clock around the ADB subprocess; includes command and transport overhead |
| `warning` | Lines beginning with `Warning:`, joined by newlines; `None` when absent |
| `raw_output` | Original stdout for troubleshooting |

`parse_am_start_output()` requires a supplied `host_elapsed_ms`. Present timing fields
must contain digits; invalid values raise `LaunchError`. Missing values remain `None`,
including when Android reports that the current task was brought to the front.

`launch_activity()` defaults to a 30-second subprocess timeout and rejects empty serials.
It raises `LaunchError` on timeout, nonzero ADB exit, stdout beginning with `Error:`, or
a parsed status other than `ok` or `None`. It parses stdout only. `get_app_pid()` uses
`pidof` with a 10-second timeout; empty output with exit code 0 or 1 means no process.
It rejects multiple PIDs, invalid integers, and other nonzero exits. PID lookup timeouts
remain `subprocess.TimeoutExpired`; missing ADB remains `FileNotFoundError`.

### Displayed events

`parse_displayed_events()` accepts supplied Logcat text and returns `DisplayedEvent`
objects with component and duration in milliseconds. For example, the unit test parses
`Displayed com.example.androidcookbook.fixture/.MainActivity: +1s234ms` as `1234` ms. The parser supports
`+<milliseconds>ms` and `+<seconds>s<milliseconds>ms` and ignores nonmatching lines.
Unit tests cover both duration formats and unrelated log lines.

The integration tests do not collect or assert `Displayed` events. There is no polling
helper for them or automatic component filtering. A hot launch need not produce a new
event. These values and host elapsed time are separate observations; the suite does not
assert relationships between timing metrics.

## Run the tests

```bash
PYTHONPATH=src poetry run pytest tests/unit/test_activity_launch_diagnostics.py -v
PYTHONPATH=src poetry run pytest \
  tests/integration/test_activity_launch_diagnostics.py \
  -m "integration and destructive" -v -s -rs
```

The unit tests cover optional and invalid timings, cold/warm/hot classification, four invalid
observations, Displayed parsing, launch command construction, host timing, launch timeout,
PID presence/absence, finish arguments, and polling success, timeout, zero-timeout,
argument validation, and predicate error propagation.

The three integration tests exercise the scenarios above and print `TotalTime` and
`HostElapsed` with `-s`. They do not require timing fields to exist or assert timing
thresholds. Default pytest runs exclude these destructive tests.

For commit verification, follow [Commit Manual](../../CommitManual.md#run-the-full-integration-suite).
Rebuild the APK, leave only the dedicated emulator online, and run the complete suites:

```bash
PYTHONPATH=src poetry run pytest tests/unit
PYTHONPATH=src poetry run pytest tests/integration -m integration -v -rs
git diff --check
```

All tests must pass without failures, errors, skips, or deselection before committing.
A warm/hot precondition skip explains an unavailable scenario but does not satisfy this
requirement. Targeted recipe runs do not replace the complete suites. Confirm teardown
leaves the fixture package absent.

## Known limitations

- Warm and hot setup depend on Android keeping the process alive. PID values may later
  be reused, and Logcat snapshots can lose events. These tests rely on short, isolated
  observation windows and fixture UUIDs.
- `LaunchState` and timing fields can vary by device output. The suite retains optional
  values and raw output; it produces no CSV/JSON artifacts or statistical benchmark.

Repeated sampling, environment metadata, percentiles, and regression detection remain
future work without an assigned release version.
