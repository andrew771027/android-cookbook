# Android Cookbook v0.5.4 — Activity Launch Diagnostics

## Overview

This recipe introduces Android Activity launch diagnostics using ADB, Activity Manager, Logcat and pytest.

The goal is to classify and observe Cold, Warm and Hot Start scenarios while collecting startup timing information.

This version focuses on diagnostics rather than performance benchmarking.

## Learning Objectives

- Understand Cold, Warm and Hot Start
- Measure launch timing using `am start -W`
- Observe application process identity
- Observe Activity instance identity
- Correlate lifecycle events with launch scenarios
- Parse Activity Manager timing output
- Distinguish startup diagnostics from benchmarking

## Architecture

```text
Host Workstation
    |
    +-- pytest
          |
          +-- Scenario Setup
          |     |
          |     +-- Cold: Force-stop
          |     +-- Warm: Finish Activity
          |     +-- Hot: Move to background

          |     |
          |     +-- adb shell am start -W
          |
          +-- Observation
          |     |
          |     +-- Process PID
          |     +-- Activity instance ID
          |     +-- Lifecycle Logcat
          |     +-- Displayed Logcat
          |
          +-- Validation
                |
                +-- Launch classification
                +-- Timing collection
```

## Startup Types

| Type | Process Before | Activity Before | Expected Behavior |
|---|---|---|---|
| Cold | Absent | Absent | Create process and Activity |
| Warm | Present | Absent | Create Activity in existing process |
| Hot | Present | Present | Resume existing Activity |

The expected behavior must be verified through runtime observations.

## Scenario A — Cold Start

Prepare:

```bash
adb shell am force-stop \
  com.example.androidcookbook.fixture
```

Verify that the application process is absent.

Launch:

```bash
adb shell am start -W \
  -n com.example.androidcookbook.fixture/.MainActivity
```

Observe:

- New PID
- New Activity instance
- `onCreate → onStart → onResume`
- Activity Manager timing

## Scenario B — Warm Start

Launch the fixture, then gracefully finish its Activity:

```bash
adb shell am start -W \
  --activity-single-top \
  -n com.example.androidcookbook.fixture/.MainActivity \
  --ez cookbook_finish true
```

Verify that the original Activity is destroyed but its process remains alive.

Launch again:

```bash
adb shell am start -W \
  -n com.example.androidcookbook.fixture/.MainActivity
```

Expected observations:

- Same PID
- New Activity instance
- New `onCreate`
- Startup timing

If the process is no longer present, the Warm Start precondition has not been established.

## Scenario C — Hot Start

Move the running Activity to the background:

```bash
adb shell input keyevent KEYCODE_HOME
```

Launch again:

```bash
adb shell am start -W \
  -n com.example.androidcookbook.fixture/.MainActivity
```

Expected observations:

- Same PID
- Same Activity instance
- No new `onCreate`
- Existing Activity resumes

The timing output may omit some fields.

## Timing Metrics

| Metric | Source |
|---|---|
| ThisTime | Android Activity Manager |
| TotalTime | Android Activity Manager |
| WaitTime | Android Activity Manager |
| Host elapsed | Python monotonic clock |
| Displayed | Android system Logcat |

Do not assume these metrics are interchangeable.

Missing timing values must be represented as missing, not zero.

## Test Strategy

### Unit Tests

Validate:

- Timing parser
- Missing fields
- Invalid values
- Launch classification
- Displayed event parser
- ADB command construction
- Timeout handling

```bash
pytest tests/unit/test_activity_launch_diagnostics.py -v
```

### Integration Tests

Validate:

- Cold Start process creation
- Warm Start Activity recreation in the existing process
- Hot Start Activity reuse
- Lifecycle observations
- Timing collection

```bash
export ANDROID_SERIAL=emulator-5554

pytest \
  tests/integration/test_activity_launch_diagnostics.py \
  -m "integration and destructive" \
  -v -s
```

## Test Isolation

Integration tests require exclusive access to:

- Foreground Activity
- Application process
- Logcat
- Emulator lifecycle state

Do not run these tests concurrently on the same Emulator.

## Best Practices

1. Verify startup preconditions before launching.
2. Do not classify startup types using timing thresholds.
3. Keep timing fields optional.
4. Use monotonic clocks for Host elapsed measurements.
5. Keep command execution, parsing and assertions separate.
6. Preserve raw Activity Manager output for troubleshooting.
7. Do not use `am start -S` for Warm or Hot Start.
8. Avoid interpreting missing `Displayed` events as startup failures.
9. Verify Activity identity using structured fixture logs.
10. Record environment metadata before comparing performance.

## Limitations

- Warm Start is not guaranteed after Activity finish.
- Android may reclaim a background process.
- Hot Start may not generate a new Displayed event.
- `am start -W` is not a complete benchmark.
- Host elapsed includes ADB overhead.
- Logcat is not a durable event store.
- LaunchState and timing fields may vary by Android version.
- PID values can eventually be reused.
- Results are not directly comparable across different host environments.
