# v0.5.1: Observe Activity lifecycle callbacks

Use the test APK and Logcat to observe Activity callbacks, then verify their order
with Python. This recipe covers launch, Home, return from Home, and graceful finish.
It uses ADB and pytest without a UI automation framework.

The current v0.5.2 fixture retains these lifecycle callbacks and uses the v0.5.2 log
marker shown below. Rebuild the APK before running this recipe. For rotation and saved
state, see [Activity recreation](v0.5.2-activity-recreation.md).

## Before you begin

Install the [project dependencies](../environment.md) and prepare a dedicated emulator
running Android API 31 or later. Build the fixture with JDK 17, the Gradle 9.3.1
Wrapper, Android SDK Platform 36, and Build Tools 36.0.0. See
[Build the test APK](v0.4.2-test-apk-fixture.md#build-the-test-apk) for setup.

Run commands from the repository root:

```bash
poetry install
./scripts/build-test-apk.sh
export ANDROID_SERIAL=emulator-5554
adb -s "$ANDROID_SERIAL" get-state
```

The last command should print `device`. Keep the emulator unlocked and run these
tests sequentially. They clear the shared Logcat buffer and change the foreground
Activity; other automation can interfere with the observations.

Rebuild with `./scripts/build-test-apk.sh` whenever the fixture source changes.
The script copies the APK to `tests/fixtures/test-app/cookbook-test-app.apk`, which
is the artifact pytest installs. Running `installDebug` alone does not refresh it.

## 1. Read the fixture logs

The fixture exports `com.example.androidcookbook.fixture/.MainActivity`. Each Activity
object has its own UUID and records these callbacks with `Log.i()`:

| Callback | Observation |
| --- | --- |
| `onCreate` | A new Activity instance is initialized |
| `onStart` | The Activity becomes visible |
| `onResume` | The Activity enters the resumed state |
| `onPause` | The Activity leaves the resumed state |
| `onStop` | The Activity is no longer visible |
| `onRestart` | A stopped Activity starts again |
| `onDestroy` | The Activity is destroyed through the normal lifecycle |

For a manual check, install and launch the fixture:

```bash
adb -s "$ANDROID_SERIAL" install -t tests/fixtures/test-app/cookbook-test-app.apk
adb -s "$ANDROID_SERIAL" logcat -c
adb -s "$ANDROID_SERIAL" shell am start -S -W \
  -n com.example.androidcookbook.fixture/.MainActivity
adb -s "$ANDROID_SERIAL" logcat -d -s CookbookLifecycle:I '*:S'
```

Example log messages, with timestamps and process fields omitted:

```text
CookbookLifecycle: marker=android-cookbook-v0.5.2 instance=11111111-1111-1111-1111-111111111111 event=onCreate
CookbookLifecycle: marker=android-cookbook-v0.5.2 instance=11111111-1111-1111-1111-111111111111 event=onStart
CookbookLifecycle: marker=android-cookbook-v0.5.2 instance=11111111-1111-1111-1111-111111111111 event=onResume
```

The UUID varies on each new instance. The parser requires `CookbookLifecycle` in the
line and the fields `marker`, `instance`, and `event` in that order, separated by
whitespace. The marker must be `android-cookbook-v0.5.2`; `instance` accepts hexadecimal
characters and hyphens. Unknown callbacks and unrelated or malformed lines are ignored.
The key is `marker=`, including the `r`; `maker=` will not match.

## 2. Observe transitions

After the initial launch, use these commands in order. Read Logcat after each action
with the command from step 1.

| Action | Expected ordered callbacks for the original instance |
| --- | --- |
| Launch with `am start -S -W` | `onCreate`, `onStart`, `onResume` |
| Press Home | `onPause`, `onStop` |
| Return without `-S` | `onRestart`, `onStart`, `onResume` |
| Request graceful finish while foreground | `onPause`, `onStop`, `onDestroy` |

Press Home:

```bash
adb -s "$ANDROID_SERIAL" shell input keyevent KEYCODE_HOME
```

Return to the existing Activity:

```bash
adb -s "$ANDROID_SERIAL" shell am start -W \
  -n com.example.androidcookbook.fixture/.MainActivity
```

Request graceful finish:

```bash
adb -s "$ANDROID_SERIAL" shell am start -W --activity-single-top \
  -n com.example.androidcookbook.fixture/.MainActivity \
  --ez cookbook_finish true
```

The foreground Activity receives the Boolean extra through `onNewIntent()` and calls
`finish()`. The extra is handled in `onNewIntent()`, so launch the Activity first.
Finishing the Activity does not uninstall its package.

The return-from-Home test requires the original instance to survive. Configuration
changes, process death, or other automation can invalidate that assumption.
Force-stop is a separate operation from graceful finish: the tests do not require
`onDestroy` when terminating a process. The four lifecycle integration tests do not
include a force-stop callback scenario; process checks belong to the
[Activity Manager recipe](v0.5.0-activity-manager.md).

After manual checks, remove the fixture before running pytest:

```bash
adb -s "$ANDROID_SERIAL" uninstall com.example.androidcookbook.fixture
```

## 3. Collect and match events in Python

`activity_lifecycle.py` provides the following helpers:

| Helper | Behavior |
| --- | --- |
| `clear_logcat(serial)` | Clear the device Logcat buffer; use only on a dedicated emulator |
| `read_lifecycle_logcat(serial)` | Return a filtered buffer snapshot without clearing it |
| `parse_lifecycle_events(output)` | Return `LifecycleEvent(instance_id, name)` objects in log order |
| `event_names(events, instance_id=...)` | Extract callback names, optionally for one instance |
| `contains_ordered_sequence(actual, expected)` | Match an ordered subsequence, allowing intervening events |
| `wait_for_lifecycle_sequence(serial, expected, ...)` | Poll snapshots until the sequence is present |
| `find_created_instance(events)` | Return the first instance with an `onCreate` event |
| `press_home(serial)` / `press_back(serial)` | Send `KEYCODE_HOME` / `KEYCODE_BACK` |
| `request_activity_finish(serial, package_name, activity_name)` | Send the foreground single-top finish request; defaults to the fixture component |

`wait_for_lifecycle_sequence()` polls every 0.2 seconds with a 10-second observation
timeout by default. It parses the full snapshot on each poll rather than accumulating
copies of previous events. `instance_id` filters the names used for matching; the
returned list still contains all parsed instances. An empty expected sequence matches
immediately after the first read.

Each lifecycle ADB command has a separate 20-second timeout and uses an explicit
serial. A blank serial, a negative observation timeout, a nonpositive poll interval,
or an unsupported key code raises `ValueError`. ADB timeouts and nonzero exits raise
`LifecycleError`; command failures include stdout and stderr. Missing ADB raises
`FileNotFoundError`.

An observation timeout raises `LifecycleError` with `expected` and `actual` callback
names. Because each ADB read can take time, the observation timeout is not a strict
wall-clock bound. `find_created_instance()` also raises `LifecycleError` if no
`onCreate` event is available.

## 4. Run the tests

The test commands in this recipe are targeted development checks. Before every
commit, follow the [full commit verification procedure](../../CommitManual.md#run-the-full-integration-suite):
rebuild the APK, run all unit tests and the entire integration suite (including
destructive tests), and require every test to pass without skips or deselection.
Use only a dedicated online emulator and run sequentially.

Unit tests need no emulator:

```bash
PYTHONPATH=src poetry run pytest tests/unit/test_activity_lifecycle.py -v
```

They cover parsing, ignored lines and unknown callbacks, multiple instances, ordered
subsequences, creation lookup, successful polling, observation timeout, accepted and
rejected key events, and finish command construction. They replace device calls with
sample responses; they do not directly test the subprocess runner's error paths or
all argument validation branches.

Run all four lifecycle integration tests:

```bash
export ANDROID_SERIAL=emulator-5554
PYTHONPATH=src poetry run pytest tests/integration/test_activity_lifecycle.py \
  -m "integration and destructive" -v
```

`pytest.ini` excludes destructive tests by default, so the explicit marker expression
is required. Shared fixtures skip when the APK is missing, or the serial is unset,
is not an `emulator-*` serial, or is unavailable. They fail if the fixture package is
already installed.

Each test installs the APK with `-t`, verifies package presence, and clears Logcat.
Launch uses `start_activity(..., force_stop_before_start=True)`, then waits for
`onCreate`, `onStart`, and `onResume`. The first creation event identifies the instance
used for later assertions:

| Test | Assertion |
| --- | --- |
| `test_activity_luanch_lifecycle` | The instance's first three callbacks are create, start, and resume |
| `test_home_triggers_pause_and_stop` | Launch is followed by pause and stop for the same instance |
| `test_return_from_home` | The stopped instance restarts, starts, and resumes, with only one creation |
| `test_graceful_finish_triggers_destroy` | The instance pauses, stops, and is destroyed; its package remains installed |

Teardown attempts force-stop, then uninstallation even if force-stop fails. Cleanup
failures remain visible. A successful run reports `4 passed`.

## Troubleshoot missing events

If `actual=[]`, inspect raw logs with the filtered Logcat command in step 1. Check the
marker spelling and version, then rebuild the APK with `./scripts/build-test-apk.sh`.
An older APK can launch successfully while emitting no matching lifecycle logs.

If only part of the sequence appears, check the foreground Activity, emulator lock
state, and instance UUID. `am start -W` returning does not guarantee that every callback
has already been logged; polling waits for those events. Avoid concurrent Logcat
clearing or navigation during the test.

Logcat snapshots are observations, not a durable event store. Ordered matching allows
extra callbacks and does not validate a complete lifecycle state machine. Back key
command construction is covered by unit tests; Back behavior, recreation, saved state,
and process death are outside the four integration scenarios.
