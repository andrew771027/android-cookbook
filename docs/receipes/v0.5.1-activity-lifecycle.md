# Android Cookbook v0.5.1 — Activity Lifecycle Observation

## Overview

This recipe introduces Android Activity lifecycle observation using a controlled test application, Android Debug Bridge (ADB), Logcat, and pytest.

The goal is to observe and validate Activity lifecycle transitions without Appium or UI automation.

## Prerequisites

- Android Environment v0.4.x
- Android SDK Platform 36
- A running dedicated Android Emulator
- Android Cookbook v0.5.0
- Updated v0.5.1 Test APK Fixture
- Python and pytest

## Architecture

```text
Android Emulator
    |
    +-- Activity Manager
    |       |
    |       +-- Start Activity
    |       +-- Home / Resume
    |       +-- Finish Activity
    |
    +-- Fixture MainActivity
    |       |
    |       +-- Lifecycle Callbacks
    |       |
    |       +-- android.util.Log
    |
    +-- Logcat
            |
            v
      Python Collector
            |
            v
      Lifecycle Parser
            |
            v
      pytest Assertions
```

## Lifecycle Callbacks

| Callback | Description |
|---|---|
| `onCreate()` | Initializes a new Activity instance |
| `onStart()` | Activity becomes visible |
| `onResume()` | Activity enters the resumed state |
| `onPause()` | Activity leaves the resumed state |
| `onStop()` | Activity becomes no longer visible |
| `onRestart()` | A stopped Activity is restarting |
| `onDestroy()` | Activity instance is being destroyed through the normal lifecycle |

The Android operating system does not guarantee that `onDestroy()` is called when an application process is killed.

## Test Scenarios

### Scenario 1 — Activity Launch

Action:

```bash
adb shell am start -S -W \
  -n com.example.androidcookbook.fixture/.MainActivity
```

Expected sequence:

```text
onCreate
onStart
onResume
```

### Scenario 2 — Home

Action:

```bash
adb shell input keyevent KEYCODE_HOME
```

Typical sequence:

```text
onPause
onStop
```

The Activity usually remains in the stopped state.

### Scenario 3 — Return from Home

Action:

```bash
adb shell am start -W \
  -n com.example.androidcookbook.fixture/.MainActivity
```

Typical sequence when the existing instance is retained:

```text
onRestart
onStart
onResume
```

### Scenario 4 — Graceful Finish

Action:

```bash
adb shell am start -W \
  --activity-single-top \
  -n com.example.androidcookbook.fixture/.MainActivity \
  --ez cookbook_finish true
```

The fixture receives the finish request through `onNewIntent()` and calls `finish()`.

Expected sequence for the original Activity instance:

```text
onPause
onStop
onDestroy
```

### Scenario 5 — Force-stop

Action:

```bash
adb shell am force-stop \
  com.example.androidcookbook.fixture
```

The application process is terminated.

Do not require an `onDestroy()` event for this scenario.

## Logcat

Lifecycle logs use the tag:

```text
CookbookLifecycle
```

Each event includes:

- marker
- Activity instance ID
- callback name

Example:

```text
marker=android-cookbook-v0.5.1 instance=... event=onResume
```

Collect logs:

```bash
adb logcat -d -s CookbookLifecycle:I '*:S'
```

The test parser uses instance IDs to distinguish events from different Activity objects.

## Testing Strategy

### Unit Tests

Unit tests mock ADB execution and validate:

- Logcat parsing
- event filtering
- ordered lifecycle sequences
- instance identity
- timeout handling
- command construction

Run:

```bash
pytest tests/unit/test_activity_lifecycle.py -v
```

### Integration Tests

Integration tests use a dedicated Android Emulator.

Run:

```bash
export ANDROID_SERIAL=emulator-5554

pytest \
  tests/integration/test_activity_lifecycle.py \
  -m "integration and destructive" \
  -v
```

Tests must clean up the fixture package after execution.

## Test Isolation

Logcat is a shared device-level resource.

The current implementation assumes:

- one dedicated Emulator
- sequential lifecycle tests
- no concurrent tests clearing Logcat
- no unrelated automation manipulating the foreground Activity

For parallel execution, use separate Emulator instances or a per-test event correlation mechanism.

## Important Limitations

- Activity callbacks are not equivalent to Process lifecycle events.
- Force-stop does not guarantee `onDestroy()`.
- Home and Back navigation can differ across Android versions.
- Activity recreation can happen because of configuration changes.
- `am start -W` does not guarantee all asynchronous UI work is complete.
- Logcat is an observation mechanism, not a durable event store.
- The current parser validates ordered events, not a complete formal state machine.
