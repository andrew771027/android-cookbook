# Android Cookbook v0.5.3 — Process Death & State Recovery

## Overview

This recipe explores Android application process death, Activity recreation, and transient UI state recovery.

It builds on v0.5.2, which introduced configuration changes and `savedInstanceState`.

The primary goal is to distinguish three scenarios:

- Activity recreation without process death
- Background process death followed by Activity restoration
- Package-level force-stop

## Learning Objectives

Understand:

- Android application process identity (PID)
- Activity instance identity
- The difference between Activity and Process lifecycles
- Background process termination through Activity Manager
- Saved instance state recovery after eligible process death
- The difference between `am kill` and `am force-stop`

## Scenario A — Activity Recreation

A configuration change may destroy and recreate an Activity while retaining the same application process.

Expected observations:

```text
Before:
PID = 1234
Activity instance = A
Counter = 5

After:
PID = 1234
Activity instance = B
Counter = 5
```

This is Activity recreation, not process death.

## Scenario B — Background Process Death

1. Launch the fixture Activity.
2. Increment counter to 5.
3. Move the Activity to the background.
4. Observe saved state.
5. Request background process termination.
6. Verify the original process is absent.
7. Relaunch the application through its Launcher intent.
8. Inspect the new PID, Activity instance and restored state.

Commands:

```bash
adb shell input keyevent KEYCODE_HOME

adb shell am kill \
  com.example.androidcookbook.fixture

adb shell pidof \
  com.example.androidcookbook.fixture
```

A successful `am kill` command does not guarantee process termination.

The test must explicitly verify that the process disappeared.

## Scenario C — Force-stop

Command:

```bash
adb shell am force-stop \
  com.example.androidcookbook.fixture
```

Force-stop is a package-level operation.

It is not equivalent to ordinary background process death.

Do not require `onDestroy()` to be called.

Do not assume that a previously saved Activity Bundle remains available.

## State Recovery

The fixture uses:

```java
outState.putInt("counter", counter);
```

and:

```java
counter = savedInstanceState.getInt("counter", 0);
```

Recovery should be evaluated using:

- Original PID
- New PID
- Original Activity instance ID
- New Activity instance ID
- Original counter
- Restored counter
- `restored` flag

A new PID alone does not prove successful state restoration.

Integration tests require a dedicated Emulator.

Do not run these tests in parallel against the same device.

## Cleanup

The test fixture must:

1. Stop the test application.
2. Uninstall the disposable fixture package.
3. Report cleanup failures.

The test must not modify or terminate unrelated applications.

## Limitations

- `am kill` may not terminate a process considered important.
- Process death does not guarantee saved state recovery.
- Task preservation and relaunch behavior can vary.
- `onDestroy()` is not guaranteed during process death.
- Force-stop is not a substitute for background process death.
- `savedInstanceState` is not persistent storage.
- PID values can eventually be reused by the operating system.
- Logcat is not a durable event store.
